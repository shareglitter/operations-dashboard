# CLAUDE.md — Glitter Ops Dashboard

Project context for Claude Code (and any human) picking this up. For end-user /
deployment instructions, see [README.md](README.md); this file focuses on **how it
works, the Airtable API footprint, and what's next**.

## What this is

A single-page operations dashboard for Glitter's president. Cleaning volume,
revenue, block growth/churn, block health, president's KPIs, and financials —
all in one static page. It reads from **Airtable** (the only data API) and is
served as a static site on **Netlify**, typically embedded in a **Softr iframe**.

Audience: **one viewer (the president), roughly weekly.** Every design tradeoff
below is calibrated to that — low traffic, correctness and low-maintenance over
scale.

## Architecture

- **`index.html`** — the whole app. Vanilla JS + Chart.js (loaded from CDN). No
  build step. Historical data is baked in via the `data.js` / `health_data.js` /
  `financials_data.js` script tags; the **current month** is fetched live from
  Airtable on load.
- **`data.js`, `health_data.js`** — auto-generated monthly caches of completed-month
  data. Do not hand-edit; they're regenerated by `refresh.js`.
- **`financials_data.js`** — financial actuals / pro-forma assumptions (hand-maintained).
- **`refresh.js`** — Node script that pulls all history from Airtable and rebuilds
  `data.js` + `health_data.js`. Run monthly by GitHub Actions. It also **prints**
  (never writes) the derivable OpsHub KPIs — see "President's KPIs" below.
- **`netlify/functions/at-proxy.js`** — serverless proxy. Holds the Airtable token
  server-side and paginates Airtable for the browser. The client never sees the token.
- **`.github/workflows/monthly-refresh.yml`** — GitHub Actions workflow (2nd of each
  month, 10:00 UTC) that runs `refresh.js` and commits the result. Requires the
  `AIRTABLE_TOKEN` GitHub secret to be set, or the job fails.

  - Blocks `tblssvtXzgL200hSi` (~600–1000 rows)

Token lives in two places, never in source: **Netlify env var** (proxy runtime) and

Optional second GitHub secret: `SLACK_WEBHOOK_URL` — see "President's KPIs".

## Airtable API footprint

Two independent paths hit Airtable. Airtable's binding limit is **5 requests/second
per base** (breach → 429 + 30s lockout); there is no monthly request-count cap on
paid plans, so burst rate is the only real constraint.

**1. Monthly refresh (`refresh.js`, server-side, ~once/month):** full-table pulls
paginated at 100/page — Cleaning Log (~486 requests) + Blocks ×3 (~18–30) +
Active Subscriptions (~16, for the KPI print). ~530 sequential requests in a
couple of minutes, off-hours.

**2. Live dashboard (`index.html`, per page load):** on load, ~14–18 requests
(current-month cleans + all blocks). First visit to the Metrics tab adds ~8 (and
hits the OpsHub base), Financials adds ~6. All lazy and guarded by `metricsLoaded` /
`financialsLoaded` so they fire at most once per session. **No polling / no
setInterval.** Failures degrade gracefully to the cached historical data.

At one viewer/week this is trivially within limits.

## Work done (2026-07)

Hardening pass focused on the API footprint:

1. **Client-side response cache** (`index.html`, `atProxy`) — 15-min localStorage
   TTL keyed by request payload. A reload/reopen within the window reuses results
   instead of re-pulling. Only successful responses are cached; failures throw
   before caching, so a transient error is never pinned for the TTL.
2. **429 / 5xx retry with backoff** — added to both `refresh.js` (`fetchAirtable`,
   plus a ~220ms inter-page throttle to stay under 5 req/s on the ~486-page cleaning
   pull) and the live proxy (`at-proxy.js`, `fetchAirtable`). Honors `Retry-After`.
   Real 4xx (e.g. 422 bad field name) are **not** retried — they pass straight to the
   existing error path that surfaces Airtable's actual message.

## President's KPIs (OpsHub → Monthly Metrics)

The OpsHub `Monthly Metrics` table is **hand-maintained** — nothing writes to it.
Several field descriptions claim "Auto-filled by refresh script", which was an
intention, not a fact: `refresh.js` only ever read the cleaning base.

`buildMonthlyMetrics()` now closes most of that gap by **printing** the derivable
values at the end of a refresh, for manual paste into the month's row. It stays
read-only on purpose — a bad computation must never corrupt the president's KPIs.

Nobody reads the Actions log, so the same block is also **posted to Slack** via
`postToSlack()` when the `SLACK_WEBHOOK_URL` secret is set (a Slack Incoming
Webhook; add it under GitHub → Settings → Secrets → Actions, and pass it in the
workflow env — already wired). Without the secret it just prints. The Slack post
is best-effort and never fails the refresh. Whoever maintains OpsHub pastes the
values into the month's row; **until that happens the Metrics tab keeps showing
the previous month**, because it picks the latest row with an Actual.

Definitions (reverse-engineered from the June 2026 row and confirmed with the
president). A **core** block is `Funding Type` ∈ Resident / Community /
Commercial, i.e. not project- or grant-funded; it is **funded/active** once
`Funding Level (with Override and Cap)` ≥ 0.25 (0.25 = monthly … 1.0 = weekly):

- `Funded Blocks` = count of funded core blocks
- `Cleaning Health %` = straight average of those blocks' levels × 100
- `Cleaning Equivalents` = sum of levels × 4 (expected cleans per billing cycle)
- `Block Growth %` = MoM change in `core_active` ÷ prior `core_active`
- `Monthly Churn %` = `churned_core` ÷ prior `core_active` — core only, so a
  month of project blocks rolling off doesn't read as core churn
- `Active Subscriptions` = live count where `Contribution Status = Active`

Still manual: `Cleaner Churn %` (needs a Cleaners table), `Partnerships`,
`Grants $`. `Backlog Reduced %` could be derived from the OpsHub Tasks table.

The three block-state metrics are **snapshots of Blocks as it stands right now**,
not as of month end — they cannot be back-computed. Run the refresh promptly.

## Block growth: three kinds, 42-day window

`buildBlockSeries` (and the live current-month mirror in `index.html`
`fetchBlockData`) classify every block one of three ways — `blockKind()`:

- **core** — Funding Type Resident / Community / Commercial, no `Projects` tag
- **spons** (sponsored) — core Funding Type *but* a `Projects` tag (Area32,
  TCB South St, WPNA…). Neighbor-funded blocks inside a project: somewhere
  between true core and true grant, so they get their own line
- **proj** — Funding Type = Project (SSNE / SSW / SSNW grants etc.)

Rows carry `core_/spons_/proj_active`, `new_*`, `churned_*` and totals. The
president's Block Growth % and Monthly Churn % stay **core-only**; the Block
Health tab and the Funded Blocks KPI still count sponsored blocks as core
(Funding Type only). That asymmetry is deliberate — Sep 2026 reconciliation:
446 funded vs 391 growth-active core = 35 sponsored + 17 stale + 11 never
cleaned − 8 cleaned-but-unfunded.

A block is active in a month if its last clean is within **`CHURN_DAYS` = 42**
days of month end (was 35). 42 lets a once-every-4-weeks block survive a
two-week slip; the 11-block Community cohort cleaned Jul 21–22 fell out of
August under 35. Keep `CHURN_DAYS` identical in `refresh.js` and `index.html`.

Blocks with the **`Exclude from Dashboard`** checkbox (placeholders / test
blocks — ImpactFund, 1300Walnut as of Sep 2026) are skipped by every
block-level series, the Block Health tiers, the Funded Blocks KPIs and the
overdue-clean check (`keepBlock()` in refresh.js, the `kept` filter in
`fetchBlockData`). Cleaning Log rows are not filtered.

Because the series is rebuilt from Airtable's *current* state, past months can
shift between runs when block records are edited (dates set, cleaning rows
relinked). Two runs two days apart moved Aug core active 389 → 391. Nothing
snapshots per-block state, so such shifts can't be traced after the fact.

## Block dates: why first and last come from different fields

`buildBlockSeries` reads **`First Clean Date`** (automation-filled) but
**`Last Clean Date [Rollup]`** (a MAX rollup over linked Cleaning Log rows).
That asymmetry is deliberate.

The automation `New Cleaning Log: Last Clean Date & Send Email Notification`
found the block via *Block Code contains …*, so a clean on `2300South` also
stamped `2200-2300South`. Every such pair left one block looking dormant (it
churned in the dashboard while being cleaned normally) and its superset twin
looking immortal. The match was fixed in Aug 2026, but 38 blocks still carry
bad dates; the rollup is immune by construction.

`First Clean Date` stays on the automation field because ~13 blocks were
backfilled to **2022-10-06** with no linked cleaning rows that old (the
`800S12th` / `1100Christian` / `1200Catharine` cohort). Switching it to the
rollup erases them from 45 months of history and re-books them as new in the
month they were first linked — a fake +12 onboarding spike in Jul 2026.
Resolve those blocks' linkage before considering the switch.

Note the rollup renders in **UTC**; set its field formatting to
America/New_York or ~80 blocks shift by a day.

## Next steps / deferred

**Deferred: single-request current-month summary (rollup).** `fetchCurrentMonthCleans`
([index.html](index.html)) pulls ~836 current-month rows just to compute 8 aggregates
split core/project/grant (counts, revenue, COGS, trash/debris bags via the categorical
`BAG_MAP`). Airtable's REST API has no GROUP BY, so collapsing this to **1 request**
requires a **month-keyed summary table** with rollups:

- On **Cleaning Log**, add formula helper fields turning categoricals into numbers:
  `Is Core / Is Project / Is Grant` (from `Project`), `Rev` (`50*Multiplier`),
  `COGS` (`IF({Payout},{Payout},25)`), `Trash Bags` / `Debris Bags`
  (`SWITCH` mirroring `BAG_MAP`), and `Month Key` (`DATETIME_FORMAT(...,"YYYY-MM")`).
- Create a **Monthly Cleaning Summary** table, one row per month, linked from
  Cleaning Log via a find-or-create automation on `Month Key`. Add `SUM(values)`
  **rollups** for each helper field.
- Then `fetchCurrentMonthCleans` becomes a single filtered fetch of one summary row.

**Verdict: not worth it at current usage** (one viewer/week; saves ~7 requests/week
and adds a fragile automation). Build it only if the dashboard opens to more viewers
or lands on a high-traffic embed. Full field-by-field recipe is in the chat history
that produced this file.

**Other loose ends:**
- Verify the `AIRTABLE_TOKEN` GitHub secret is set — the monthly workflow (now at
  `.github/workflows/`) needs it. Before the workflow was moved there it never ran,
  so `data.js` history may only be as fresh as the last manual `node refresh.js`.
- `financials_data.js` is hand-maintained — update it when new actuals land.
- `index copy.html` is a stale backup; delete once you're confident in `index.html`.

## Conventions

- No build step, no framework, no npm install for the app itself — keep it that way.
- The Airtable token must never appear in any committed file or client-side code.
- All Airtable access from the browser goes through `at-proxy.js`, never direct.
- `data.js` / `health_data.js` are generated — regenerate via `refresh.js`, don't hand-edit.
