# CLAUDE.md — Glitter Ops Dashboard

Project context for Claude Code (and any human) picking this up. For end-user /
deployment instructions, see [README.md](README.md); this file focuses on **how it
works, the Airtable API footprint, and what's next**.

## What this is

A single-page operations dashboard for Glitter's president. Cleaning volume,
revenue, block growth/churn, block health, president's KPIs, and financials —
all in one static page. It reads from **Airtable** (the only data API) and is
served as a static site on **Netlify**, typically embedded in a **Softr iframe**.

Audience: **one viewer (the president), roughly weekly.** Every design tradeoff
below is calibrated to that — low traffic, correctness and low-maintenance over
scale.

## Architecture

- **`index.html`** — the whole app. Vanilla JS + Chart.js (loaded from CDN). No
  build step. Historical data is baked in via the `data.js` / `health_data.js` /
  `financials_data.js` script tags; the **current month** is fetched live from
  Airtable on load.
- **`data.js`, `health_data.js`, `health_history.js`** — auto-generated caches.
  Do not hand-edit; they're regenerated by `refresh.js`. `health_history.js` is
  append-only across runs — see "Block health history".
- **`financials_data.js`** — financial actuals / pro-forma assumptions (hand-maintained).
- **`refresh.js`** — Node script that pulls all history from Airtable and rebuilds
  `data.js` + `health_data.js`. Run monthly by GitHub Actions. It also **prints**
  (never writes) the derivable OpsHub KPIs — see "President's KPIs" below.
- **`netlify/functions/at-proxy.js`** — serverless proxy. Holds the Airtable token
  server-side and paginates Airtable for the browser. The client never sees the token.
- **`.github/workflows/monthly-refresh.yml`** — GitHub Actions workflow (2nd of each
  month, 10:00 UTC) that runs `refresh.js` and commits the result. Requires the
  `AIRTABLE_TOKEN` GitHub secret to be set, or the job fails. "Run workflow" in
  the GitHub UI has a **`health_only`** checkbox: ticked, it runs
  `refresh.js --health-only` (Blocks table only, ~10 requests), rewrites
  `health_data.js`, appends a snapshot to `health_history.js` and leaves
  `data.js` untouched.

**GitHub secret** `AIRTABLE_TOKEN` (monthly refresh). Rotate both together.
Optional second GitHub secret: `SLACK_WEBHOOK_URL` — see "President's KPIs".

## Airtable API footprint

Two independent paths hit Airtable. Airtable's binding limit is **5 requests/second
per base** (breach → 429 + 30s lockout); there is no monthly request-count cap on
paid plans, so burst rate is the only real constraint.

**1. Monthly refresh (`refresh.js`, server-side, ~once/month):** full-table pulls
paginated at 100/page — Cleaning Log (~486 requests) + Blocks ×3 (~18–30) +
Active Subscriptions (~16, for the KPI print). ~530 sequential requests in a
couple of minutes, off-hours.

**2. Live dashboard (`index.html`, per page load):** on load, ~14–18 requests
(current-month cleans + all blocks). First visit to the Metrics tab adds ~8 (and
hits the OpsHub base), Financials adds ~6. All lazy and guarded by `metricsLoaded` /
`financialsLoaded` so they fire at most once per session. **No polling / no
setInterval.** Failures degrade gracefully to the cached historical data.

At one viewer/week this is trivially within limits.

## Work done (2026-07)

Hardening pass focused on the API footprint:

1. **Client-side response cache** (`index.html`, `atProxy`) — 15-min localStorage
   TTL keyed by request payload. A reload/reopen within the window reuses results
   instead of re-pulling. Only successful responses are cached; failures throw
   before caching, so a transient error is never pinned for the TTL.
2. **429 / 5xx retry with backoff** — added to both `refresh.js` (`fetchAirtable`,
   plus a ~220ms inter-page throttle to stay under 5 req/s on the ~486-page cleaning
   pull) and the live proxy (`at-proxy.js`, `fetchAirtable`). Honors `Retry-After`.
   Real 4xx (e.g. 422 bad field name) are **not** retried — they pass straight to the
   existing error path that surfaces Airtable's actual message.

## President's KPIs (OpsHub → Monthly Metrics)

The OpsHub `Monthly Metrics` table is **hand-maintained** — nothing writes to it.
Several field descriptions claim "Auto-filled by refresh script", which was an
intention, not a fact: `refresh.js` only ever read the cleaning base.

`buildMonthlyMetrics()` now closes most of that gap by **printing** the derivable
values at the end of a refresh, for manual paste into the month's row. It stays
read-only on purpose — a bad computation must never corrupt the president's KPIs.

Nobody reads the Actions log, so the same block is also **posted to Slack** via
`postToSlack()` when the `SLACK_WEBHOOK_URL` secret is set (a Slack Incoming
Webhook; add it under GitHub → Settings → Secrets → Actions, and pass it in the
workflow env — already wired). Without the secret it just prints. The Slack post
is best-effort and never fails the refresh. Whoever maintains OpsHub pastes the
values into the month's row; **until that happens the Metrics tab keeps showing
the previous month**, because it picks the latest row with an Actual.

Definitions (reverse-engineered from the June 2026 row and confirmed with the
president). A **core** block is `Funding Type` ∈ Resident / Community /
Commercial, i.e. not project- or grant-funded; it is **funded/active** once
`Funding Level (with Override and Cap)` ≥ 0.25 (0.25 = monthly … 1.0 = weekly):

- `Funded Blocks` = count of funded core blocks
- `Cleaning Health %` = straight average of those blocks' levels × 100
- `Cleaning Equivalents` = sum of levels × 4 (expected cleans per billing cycle)
- `Block Growth %` = MoM change in `core_active` ÷ prior `core_active`
- `Monthly Churn %` = `churned_core` ÷ prior `core_active` — core only, so a
  month of project blocks rolling off doesn't read as core churn
- `Active Subscriptions` = live count where `Contribution Status = Active`

Still manual: `Cleaner Churn %` (needs a Cleaners table), `Partnerships`,
`Grants $`. `Backlog Reduced %` could be derived from the OpsHub Tasks table.

The three block-state metrics are **snapshots of Blocks as it stands right now**,
not as of month end — they cannot be back-computed. Run the refresh promptly.

## Block growth: three kinds, 42-day window

`buildBlockSeries` (and the live current-month mirror in `index.html`
`fetchBlockData`) classify every block one of three ways — `blockKind()`:

- **core** — Funding Type Resident / Community / Commercial, no `Projects` tag
- **spons** (sponsored) — core Funding Type *but* a `Projects` tag (Area32,
  TCB South St, WPNA…). Neighbor-funded blocks inside a project: somewhere
  between true core and true grant, so they get their own line
- **proj** — Funding Type = Project (SSNE / SSW / SSNW grants etc.)

Rows carry `core_/spons_/proj_active`, `new_*`, `churned_*` and totals. The
president's Block Growth % and Monthly Churn % stay **core-only**; the Block
Health tab and the Funded Blocks KPI still count sponsored blocks as core
(Funding Type only). That asymmetry is deliberate — Sep 2026 reconciliation:
446 funded vs 391 growth-active core = 35 sponsored + 17 stale + 11 never
cleaned − 8 cleaned-but-unfunded.

A block is active in a month if its last clean is within **`CHURN_DAYS` = 42**
days of month end (was 35). 42 lets a once-every-4-weeks block survive a
two-week slip; the 11-block Community cohort cleaned Jul 21–22 fell out of
August under 35. Keep `CHURN_DAYS` identical in `refresh.js` and `index.html`.

Blocks with the **`Exclude from Dashboard`** checkbox (placeholders / test
blocks — ImpactFund, 1300Walnut as of Sep 2026) are skipped by every
block-level series, the Block Health tiers, the Funded Blocks KPIs and the
overdue-clean check (`keepBlock()` in refresh.js, the `kept` filter in
`fetchBlockData`). Cleaning Log rows are not filtered.

Because the series is rebuilt from Airtable's *current* state, past months can
shift between runs when block records are edited (dates set, cleaning rows
relinked). Two runs two days apart moved Aug core active 389 → 391. Nothing
snapshots per-block state, so such shifts can't be traced after the fact.

## Block dates: derived from the Cleaning Log, as of each month end

`buildBlockSeries(byBlock)` no longer reads clean dates off the Blocks table.
`buildCleaningSeries` pulls the **`Block`** link on every Cleaning Log row (same
request, one more field) and hands back a per-block sorted list of clean
timestamps. For each month the series takes the latest clean dated **before that
month end**; a block is active if that is within `CHURN_DAYS` and its first clean
precedes month end.

Why: `Last Clean Date [Rollup]` is a present-day MAX. A block dormant all summer
and cleaned on Sep 4 read as *active in August* and its August churn vanished, so
August drifted 389 → 391 → 403 across three runs in one week, and the churn KPI
shrank the later the refresh ran. Now a completed month depends only on cleans
dated in or before it. It still moves — legitimately — when a clean is logged
late or a row is relinked to the right block; `reportShifts()` prints any
completed month that moved by more than `SHIFT_TOLERANCE` (2) since the previous
`data.js`, so a human sees it in the Actions log / Slack.

**`First Clean Date` (automation) is kept only as a floor.** ~13 blocks were
backfilled to **2022-10-06** with no linked cleaning rows that old (the
`800S12th` / `1100Christian` / `1200Catharine` cohort). First clean = the earlier
of the field and the first logged clean, so they keep their 2022 onboarding
instead of re-booking as new in the month they were first linked.

Known gaps: ~1,280 Cleaning Log rows (2.5%, newest Jul 2026) have **no Block
link** and are invisible to block growth (they were equally invisible to the
rollup). Blocks with a First Clean Date but zero linked rows are skipped.

The **live current month** in `index.html` (`fetchBlockData`) still uses the
rollup: "last clean as of now" is the right answer for the month in progress and
it avoids pulling the log client-side. The automation-filled `Last Clean Date`
field is no longer read anywhere (its substring-match bug stamped
`2200-2300South` for cleans on `2300South`; fixed Aug 2026, ~38 blocks still
carry bad dates). Note the rollup renders in **UTC**; the log-derived series
also keys months in UTC to match the cleaning series.

## Block health history (`health_history.js`)

The Block Health tab's tier distribution and heatmap are a **snapshot of the
Blocks table as it stands when `refresh.js` runs** — not live, and not
back-computable (tiers come from Airtable formulas over present-day state). So
since Oct 2026 every run of `buildHealthData` also **appends** its snapshot to
`health_history.js` (`appendHealthHistory`): `HEALTH_HISTORY` is an array of
`{date, core, proj}` with the same `{tiers, heatmap, total}` shape as
`HEALTH_DATA`. Keyed by the date the snapshot was taken; a same-day rerun
replaces that date's entry, and nothing is ever dropped (decision Oct 2026:
"date, keep everything"). The scheduled run on the 2nd is effectively an
end-of-prior-month reading; a manual `health_only` run adds a mid-month point.

The file was **seeded from git**: every monthly refresh had committed a fresh
`health_data.js`, so the seven distinct dates from 2026-07-22 to 2026-10-02 were
replayed as the first entries (latest commit per date). Same six tiers and the
same heatmap axes throughout. Caveat: the `Exclude from Dashboard` filter only
arrived in Sep 2026, so the Jul/Aug points include ~2 placeholder blocks.

The tab shows a **Trend** section above the snapshot: four tiles (core total,
funded, Tier 1–3, Tier 4–6) with deltas vs the previous and first snapshot, and
four clustered bars per snapshot — **funded blocks by cleaning level**
(Weekly / 3/4 / 2/4 / 1/4, the heatmap's column sums minus Not Funded; the
not-funded column is deliberately left off) with the count printed above
each bar (`renderHealthTrend`, `TREND_GROUPS` in `index.html`). The snapshot
headings read "as of <latest history date>" — the same run writes both files,
so the dates agree. The six-colour tier palette fails the colourblind check
(Tier 3 yellow vs Tier 4 orange); the trend uses four validated colours.

The heatmap's **Not Funded column is split in two** (Oct 2026): blocks with
some live pledge and blocks with none. "Live pledge" = the sum of `Pledge` on
the block's Active Subscriptions rows whose `Contribution Status` is Active,
Missing Payment, Pledged (Block Not Active / Not Yet Paying) or Invoice Sent
(`LIVE_PLEDGE_STATUSES`), joined on `Block Code`; churned statuses don't count.
**Don't use `Funding Level (via Pledges)` for this** — it is quantized to
0 / 0.25 / 0.5 / 1 (confirmed Oct 26, 2026: all 797 not-funded core blocks read
exactly 0), so it can't see a partial pledge. `buildHealthData` stores the split
as a separate `nfPledged` map (`{subTier: count}`) on each bucket rather than as
new `CLEAN_TIERS` values, so older history snapshots and the trend's column
sums are untouched; `renderHeatmap` falls back to the single column when a
snapshot lacks `nfPledged`, which is also what happens if the subscriptions
pull fails (the key is deleted rather than written empty). This adds ~25
requests to `--health-only`. Oct 26 probe: 327 not-funded core blocks carried
a live pledge, 218 of them under $25/cycle.

**`Block Tier (calc)` formula (read Oct 2026)** — `L` = `Funding Level (via
Pledges)`, `subs` = `Total Subscribers` (all subscriber records, not just
Active), "cleaned" = has linked Cleaning Log rows:

- Tier 1: L ≥ 1 and subs ≥ 5
- Tier 2: (L ≥ 0.5 and subs ≥ 5) or (L ≥ 1 and subs < 5)
- Tier 3: `Funding Level (with Override and Cap)` ≥ 0.25, or (L ≥ 0.5 and subs < 5)
- Tier 4: L < 0.25, subs ≥ 1, never cleaned — pledges but no cleans
- Tier 5: L < 0.25, ever cleaned — churned, **with or without pledges** (Oct
  2026 live: ~110 of ~380 still carry subscriber records)
- Tier 6: everything else — L < 0.25, no subscribers, never cleaned

So the page legend was right. Tier 5 is *not* "no pledges": about 30% of it
still has subscriber records. (The snapshot identity "Tier 5 = not-funded with
1+ subs" that looked structural was a coincidence — don't lean on it.)

## Next steps / deferred

**Deferred: single-request current-month summary (rollup).** `fetchCurrentMonthCleans`
([index.html](index.html)) pulls ~836 current-month rows just to compute 8 aggregates
split core/project/grant (counts, revenue, COGS, trash/debris bags via the categorical
`BAG_MAP`). Airtable's REST API has no GROUP BY, so collapsing this to **1 request**
requires a **month-keyed summary table** with rollups:

- On **Cleaning Log**, add formula helper fields turning categoricals into numbers:
  `Is Core / Is Project / Is Grant` (from `Project`), `Rev` (`50*Multiplier`),
  `COGS` (`IF({Payout},{Payout},25)`), `Trash Bags` / `Debris Bags`
  (`SWITCH` mirroring `BAG_MAP`), and `Month Key` (`DATETIME_FORMAT(...,"YYYY-MM")`).
- Create a **Monthly Cleaning Summary** table, one row per month, linked from
  Cleaning Log via a find-or-create automation on `Month Key`. Add `SUM(values)`
  **rollups** for each helper field.
- Then `fetchCurrentMonthCleans` becomes a single filtered fetch of one summary row.

**Verdict: not worth it at current usage** (one viewer/week; saves ~7 requests/week
and adds a fragile automation). Build it only if the dashboard opens to more viewers
or lands on a high-traffic embed. Full field-by-field recipe is in the chat history
that produced this file.

## Pilots Dashboard (`pilots.html`)

Sister page for the president's **pilot programs** — ambassadors, new service
interest (leaves / snow / weeds / trash cans), compost. Kept out of `index.html`
on purpose: the ops page is calibrated for a 48k-row log with baked history,
while the pilot tables are tens of rows that change weekly. Same Netlify site,
same `at-proxy.js`, same styles (copied, not shared — extract to a stylesheet if
the two pages keep moving together). Embed in Softr as
`https://<site>.netlify.app/pilots.html`.

**Data model: everything is fetched live on load, nothing is baked.** No
`refresh.js` involvement, no `*_data.js`. Ambassadors tab = 4 requests on load;
Service Interest and Compost tabs lazy-load on first open (1 and 3 requests).
All use server-side `filterByFormula` so the big tables (Blocks, Subscribers)
return only the handful of relevant rows. Same 15-min localStorage cache as
the ops page, keyed `pilots:at:`.

Pilot tables (cleaning base, referenced by **name** — renaming one breaks the
fetch with a 403 naming the table):
- `Ambassadors` — one row per ambassador: Name, Status, Start Date, Hourly Rate,
  links to Assigned Blocks / Shifts / Leads, rollup totals.
- `Ambassador Shifts` — Date, Ambassadors, Hours Worked, Doors Knocked, Activity
  Type (Door Knocking / Event / Admin / Training), Pay Due, Paid.
- `Ambassador Leads` — Date of Contact, Ambassador Name, Block, Neighbor
  name/email, Status (hand-set), Subscriber Record link, lookups of the
  subscriber's `Contribution Status` and `Pledge`, Commission Amount.
- `Ambassador Leads` also has `Blocks (from Subscriber Record)` (Oct 2026): the
  block of the subscription the lead became. The page attributes a lead to its
  direct `Block` link, else that lookup.
- Blocks carries `Ambassadors` / `Ambassador Leads` links and the compost fields
  `Compost Pilot` (checkbox), `Count Compost Add-On Active Subscriptions` (count),
  `Compost Pickup Day`. (`Compost Neighbors`, a hand-kept email list, is no longer read.)
- **Service interest** = flags on Subscribers synced from ActiveCampaign tags
  (Oct 2026): `Snow opt-in`, `Leaves opt-in`, `TrashCan opt-in`, `Weeds opt-in`
  (text, value "Yes"; one row carries a `||Yes||` sync artifact, still counts).
  The older signup single-select `Compost Opt-In` is charted alongside for
  reference (only values starting "Yes" count; "Not Right Now" doesn't) but is
  **excluded from the headline tiles** because compost has shipped. One request:
  `OR({Snow opt-in}, …, {Compost Opt-In})`; the "Not Right Now" rows come back
  and are dropped client-side. No date on the flags, so no trend yet — if the
  AC sync can carry the tag date, add a month series. `Services` is no longer
  read or allow-listed.
- **Converted** = the lead's linked subscriber has Contribution Status `Active`
  — confirmed as the definition, and it is also what triggers the commission
  payout. The hand-set `Status` on leads is ignored — it lags badly (Oct 2026: 36 of 43
  read "Lead" while 24 were Active). **Pending** = Invoice Sent / Pledged, Not
  Yet Paying / Pledged, Block Not Active. **Lost** = anything else with a
  subscriber link.
- **MRR added** = sum of Active leads' `Pledge` × 13⁄12 (pledge is per 4-week
  cycle) — same factor as the pledge work in `refresh.js`.
- **Program cost** = Σ `Pay Due` on shifts + Σ `Commission Amount` on leads.
  Cost per conversion and payback (cost ÷ MRR) follow from those.
- Hours are bucketed Door knocking / Events & meetings / Admin & training.
- Assigned-block funding levels are a **live snapshot**; there is no history, so
  "did the block move up a tier" can't be shown yet. **Tabled Oct 2026.** If it
  becomes the KPI, have `refresh.js` record per-block funding level monthly.
- **Compost source of truth = the `Compost Add-On` checkbox on Active
  Subscriptions** (confirmed with the user, Oct 2026). One filtered request
  (`OR({Compost Add-On}=1, FIND("Yes", {Compost Opt-In (from Subscriber)}))`,
  ~60–80 rows) — no Airtable view needed, and the proxy doesn't take a `view`
  param anyway. Buckets by `Contribution Status`: Active / pending (Pledged, Not
  Yet Paying · Pledged, Block Not Active · Invoice Sent) / churned. The month
  series keys on `Last Modified - Compost Add-On` (Apr 2026 = launch backfill).
  "Interested, not added" = Subscribers `Compost Opt-In` answered "Yes…" with no
  add-on ticked. Revenue is estimated at $15 × active add-ons. Blocks carry
  `Count Compost Add-On Active Subscriptions` (count field added Oct 2026): the
  page uses it to find blocks with add-ons (`>0`) and shows it as a cross-check
  column; it replaced the `Compost Neighbors` email list, which is no longer
  requested or allow-listed. Subscriptions on `Exclude from Dashboard` blocks
  (1300Walnut has one) are dropped, matching the ops page. An add-on on a block
  without the `Compost Pilot` flag means the block is identified but has no bin
  yet (expected). **Don't use** `Compost Pilot` on Active Subscriptions (a block
  lookup, marks everyone on a pilot block).

Known data gaps the page flags automatically: leads with no Block link, door
shifts with no Doors Knocked, ambassadors with no activity (a test duplicate was
deleted Oct 2026; new ambassadors show here until their first shift).

`node pilots_check.js` pulls the same tables through the deployed proxy, runs
the page's compute block and prints the model with consistency checks. Run it
after any Airtable field change or edit to the compute block.

## Conventions

- No build step, no framework, no npm install for the app itself — keep it that way.
- The Airtable token must never appear in any committed file or client-side code.
- All Airtable access from the browser goes through `at-proxy.js`, never direct —
  and the proxy only serves the base/table/field combinations in its `ALLOW` list.
- `data.js` / `health_data.js` / `health_history.js` are generated — regenerate via
  `refresh.js`, don't hand-edit.
